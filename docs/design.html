Feedback Autopilot

How forwarder feedback and heatmap data turn into fixed code. An agent triages, reproduces, fixes and opens the PR, and asks a developer only when it isn't sure.

Problem Architecture Shared map Build plan How to build Today's build

Two sides of one product

  • Freight forwarders (Ops, accounting) use nemox all day. When something breaks or confuses them, they click Feedback.
  • Developers build nemox. They see that feedback as a Slack message with a screenshot, often hours later and with little context.

Between the two sits a manual step: a developer reads every message, works out what happened, and only then starts on a fix.

How feedback reaches a developer today

Forwarder clicks Feedback→ Slack message + screenshot→ Developer reads it→ Finds the session in PostHog→ Reproduces→ Finds the code→ Fix + PR→ Review, merge→ Forwarder rarely hears back

Where the time goes

  • Every message interrupts a developer, including duplicates and how-to questions.
  • The screenshot shows the result, not the cause. The developer finds the user's session, the console error and the clicked element by hand.
  • The same bug arrives several times from different users, and each message is triaged again.
  • PostHog records heatmaps, rage clicks, dead clicks and errors for every session. Nobody has time to watch them daily, so problems nobody reports stay hidden.
  • The forwarder who reported it rarely learns that it was fixed.

What we build

A background agent turns each feedback message, and each problem the nightly heatmap scan finds, into a triaged issue, a failing test, a fix and a PR. Small, proven fixes merge by themselves. Everything else waits for a developer with the evidence already collected. The forwarder hears back either way.

Open questions

  • Which fixes may merge with no human? We start with copy and label fixes, and the agent earns trust per kind of fix from developer decisions.
  • Where does an auto-merge land? Straight to main, or to staging first, with the nightly check confirming the rage clicks went away?
  • How does the forwarder hear back? In-app note, email, or through customer success from the Slack thread?
  • What access does it need? A read-only PostHog key, and a GitHub app limited to the frontend repo.

Overview

Two triggers start the same agent graph: a feedback message (live) and the nightly heatmap scan. The graph ends at a merge gate. Every developer decision is saved as a label, and the nightly eval run turns those labels into a trust table that tells the gate which kinds of fixes may merge alone.

LoopWhenWhat it does
LiveEach feedback messageRuns the graph on one message. Reads past cases and trust from the label store, and saves each developer decision.
NightlyEvery nightScans PostHog for new problem spots and runs the graph on the worst ones. Replays all labelled cases and updates the trust table. Checks last week's merged fixes: if rage clicks or errors on that element did not drop, opens a revert PR for a developer.
On changeWhen we editWe change a prompt, model or the graph. Evals run on the stored cases, and the change ships only if the score holds.

The agent graph

A state machine (LangGraph) with fixed edges. Each node has one job. The LLM works only inside its nodes; tests, diffs and gate rules are plain Python, so the same input takes the same path.

  1. Collect signal tool

    Read the feedback message (text, screenshot, user, page, time), or a heatmap group from the nightly scan, into one Signal.

  2. Enrich tool

    Pull the user's PostHog session around that time: clicks, rage and dead clicks, console and network errors. Map the page URL to its route and source files.

  3. Extract issue LLM

    Read text, screenshot and events into a typed Issue: page, element, expected, actual, steps to reproduce. Similar past cases from the label store go into the prompt.

  4. Triage decision

    Duplicate? Category (bug, copy, UX, feature request, how-to), severity, and can the agent fix it, each with a probability. A duplicate is linked and its evidence added. Anything not fixable becomes an issue for a developer, with the evidence attached. If p is below CONFIDENCE_THRESHOLD, go back to Enrich for more evidence, up to MAX_RETRIES times. Still low: the graph pauses and a developer picks the category in the UI. That answer is saved as a label for the evals.

  5. Locate code tool

    Search the repo by selector, button text and route. Return the candidate files.

  6. Reproduce LLM Python

    The LLM writes a test from the steps, Python runs it, and it must fail. If it passes, the bug isn't reproduced: go back to Enrich, up to MAX_RETRIES times (default 2). Still no repro: open an issue.

  7. Fix coding agent

    A coding agent edits the candidate files in its own git worktree, on a new branch. It may touch only the app's code, never the agent itself or CI.

  8. Verify Python

    Run the new test, the full suite and lint, and measure the diff. On failure, go back to Fix, up to MAX_RETRIES times. Still failing: open an issue with the attempt attached.

  9. Open PR tool

    Push the branch and open a PR with the evidence: feedback text, screenshot, PostHog session link, and the test that failed before and passes now.

  10. Merge gate decision

    Read the trust table for this category and code area. Trusted, score above the threshold, small diff, no protected paths: auto-merge. Otherwise: ask a developer.

  11. Developer review human

    The graph pauses. A developer approves, edits or rejects the PR, and the decision is saved to the label store.

  12. Merge and notify tool

    Merge the PR. Post the result in the Slack thread and tell the forwarder it's fixed.

Tool (MCP) LLM or coding agent Python Decision model or store Human

Nightly heatmap scan

Most forwarders never click Feedback, but PostHog still records where they struggle. Each night the scan reads the last 24 hours and turns the worst spots into signals for the same graph.

  1. Pull events tool

    $rageclick, $dead_click, $exception and heatmap clicks per page, for the last 24 hours.

  2. Group Python

    By page and element selector. Exceptions also by error message.

  3. Score Python

    Users affected × events, compared with the previous 7 days. New and rising groups rank first.

  4. Pick the top N Python

    Default 3. Groups already open as an issue or PR are skipped.

  5. Attach evidence tool

    One sample session link and a heatmap snapshot per group.

  6. Run the graph graph

    Each group enters at Collect signal, like a feedback message with no text.

Why lots of heatmap data doesn't mean lots of code changes

PostHog records every click of every user, so the data grows fast. The number of code changes doesn't grow with it, for these reasons:

  • Most clicks are normal use. The heatmap records behaviour, not defects. Only rage clicks, dead clicks and errors count as problem signals, and they are a small share of all events.
  • Many events, few causes. 41 rage clicks from 9 users on one cell are one problem, not 41. Grouping by page and element turns thousands of events into a few dozen groups.
  • Only what is new or rising. Each group is compared with the previous 7 days. A pattern that was there yesterday and is already known doesn't come back as a new signal every night.
  • A fixed budget per night. Only the top N groups enter the graph (default 3). Groups already open as an issue or PR are skipped.
  • Most problems aren't code bugs. Rage clicks often mean "I expected something here". Those become issues for product, not PRs.
  • No reproduction, no PR. The agent changes code only after a test fails. If it can't reproduce the problem, a developer gets an issue with the evidence.
  • Fixed problems disappear. Once a fix ships, its signal drops out of the data. Over time there are fewer hotspots, not more.

On top of that, two hard limits: at most MAX_AUTO_MERGES_PER_DAY auto-merges (default 5), and only one open agent PR per code area, so two fixes never touch the same files at once. Auto-merged fixes ship together in one daily release, so there is one deploy to watch.

Finding regressions

Changes come from the agent and from developers. Both are checked the same way, before and after merge.

WhenCheckIf it fails
Before mergeThe new repro test failed before the fix and passes after. Every fix adds a permanent test.Back to Fix, then an issue
Before mergeFull suite and lint pass. The agent can't edit existing tests, so it can't make a test pass by changing it.Blocked
Before mergeNo protected paths: billing, auth, migrations, CI, the agent itself.Developer review
After merge, nightlyImpact check: the signal that caused the fix (dead clicks, errors on that element) is compared before and after the deploy.Revert PR for a developer
After merge, nightlyNearby signals on the same screen: new errors, fewer people finishing the top paths.Revert PR for a developer

The impact check runs on every merge, developers' too, because the heatmap doesn't know who changed the code. Deploy times and the files each PR touched show which change caused a new hotspot. A revert always goes through a developer.

Golden set: past cases with a known right answerTesting our own changes to the agent
  • Nightly: all labelled cases are replayed and the trust table is rebuilt. One revert in a category and code area makes it untrusted again, and its PRs go back to developers until it earns trust back. The system tightens itself after a mistake.
  • When we change the agent: a new prompt, model or graph runs on the golden set first, and ships only if the scores hold. This catches regressions in the agent, not just in the app.
  • Scores: triage accuracy, reproduction rate, merged unchanged, revert rate, and impact confirmed (the signal dropped after the fix).

Merge gate

A PR merges without a developer only when every check passes. Otherwise it waits for review, with the evidence attached.

CheckRule
ReproducedThe new test failed before the fix and passes after it
SuiteThe full test suite and lint pass
SizeAt most 40 changed lines in 3 files (MAX_DIFF_LINES)
PathsNo protected paths: billing, auth, migrations, CI, the agent itself
ScoreTriage and fix confidence ≥ 0.85 (CONFIDENCE_THRESHOLD)
TrustThis category and code area is trusted: at least 30 labelled cases, ≥ 95% merged unchanged, no reverts
Spot check5% of PRs that pass still go to a developer, chosen at random

Evals and feedback loop

  • Labels: every PR outcome (merged unchanged, edited, rejected, reverted) and every triage correction.
  • Scores: triage accuracy per category, reproduction rate, PRs merged unchanged, reverts, time from feedback to PR.
  • Trust table: per category and code area. "copy · frontend" can become trusted; "logic · billing" never does.
  • Similar cases: merged fixes become examples for extract and triage on the next run. Code always comes from today's repo, never from past cases.

The second half of the gap

Fixing bugs faster closes only part of the gap. The other part is that the two sides think about the product differently.

What"download the PDF for the customer"#download-pdf click handler, PDF endpoint

  • A new developer learns the code in weeks but how a forwarder works in months. They can't tell which screens matter or why.
  • A new forwarder learns the product from a colleague, and reports known issues again as new ones.
  • Neither side sees what the other already knows.

The analogy

Heatmaps, feedback and fixes together are a recording of how the product is really used. It's like a city map with live traffic:

A new hire normally learns this by shadowing the best Ops person for a month. The data already has that month in it, for every user. We turn it into a map both sides read.

How it onboards people

New developer, day 1

  • Tour of the 5 busiest screens, in the order forwarders use them, with the code behind each.
  • The forwarder words next to the code names, so feedback makes sense from day 1.
  • First task: an issue the autopilot triaged but didn't auto-fix, with evidence and a failing test already written.

New forwarder, day 1

  • How colleagues actually do each task, from the most common paths.
  • Known issues and workarounds, so they don't report them again.
  • What was fixed this week, in their words.

Both read the same card, so both talk about the same screen with the same words. Feedback gets more specific, and developers understand it faster.

How it uses the same framework

  1. List screens tool

    Routes from the repo, and pages seen in PostHog.

  2. Usage Python

    Visits, top paths, time on task, hotspots per screen.

  3. Collect tool

    Feedback, labels and PRs for this screen from the label store; files from the repo.

  4. Write card LLM

    Typed ScreenCard schema with both views, and a source for every fact.

  5. Changed? decision

    Only a real change saves a new version and posts "what changed" to the team.

It runs in the nightly trigger, after the heatmap scan. It also feeds back into the autopilot: when triage says a feedback is a how-to question, the agent answers from the card instead of pinging a developer, and the question improves the card.

One laptop or two?

Two laptops to build, one to demo.

  • The work splits cleanly: the target app and mock data don't need the agent, and the agent runs on stubs until the data lands.
  • The coding agent and LLM calls take minutes per run. On one laptop the second person would mostly watch.
  • The risk of two laptops is a painful merge at the end. Folder ownership, merges every 30 minutes and the joint checks keep that small.
  • Demo on Abubakar's laptop: it owns the repo and the gh login, so the agent's PRs open as the repo owner. From 17:50 every joint check runs there.

Git workflow

  • Branches: short-lived, abubakar/<task> and nils/<task>. Merge to main at least every 30 minutes, always before a joint check.
  • Merging: run the fast tests, pull main, push, merge your own PR. No review wait between us; the joint check is the review.
  • The agent merges into a local demo branch, never main (GITHUB_BACKEND=mock, GITHUB_BASE_BRANCH=demo). The demo app serves from a demo worktree, so a merge shows up on reload. reset.sh resets demo to main.
  • Planted bugs are frozen after M0. Nobody edits the P1–P3 lines in target-app/ by hand.
  • Secrets: each person has their own .env. Generated files (seed.sqlite) are not committed; generate.py uses a fixed seed, so both laptops have the same data.

Demo moments

Moments 1 and 3 run the same graph. The only difference is what the system learned in between.

Moment 1 · A forwarder reports a broken button

We click: Download PDF in the target app. Nothing happens. Then Feedback: "Download button does nothing." The screenshot is attached.

The graph runs: collect → enrich (6 users, 14 dead clicks on #download-pdf, TypeError) → extract → triage (bug, p 0.94, fixable) → locate target-app/app.js → repro test fails → fix → tests pass → PR opens.

Merge gate: "handler · frontend" is not trusted, so it asks a developer. We click Approve, it merges, we reload, and the button works. Slack: "Fixed in PR #1."

Say: "The forwarder wrote one line. The agent did the developer's first hour: found the session, reproduced it, fixed it. The developer only reviewed."

Moment 2 · Run nightly

First, a vague one: FB-103 "the shipments page is weird". Triage p 0.48, below 0.85. Enrich adds the session, p 0.55, still low after the last try. The graph pauses and the developer picks "UX · shipments" in the UI. Saved as a label.

We click: "Run nightly". In production cron runs python -m app.nightly.

Heatmap scan: top new group is rage clicks on the ETA cell (9 users, 41 rage clicks). Triage: UX, not a code bug. A GitHub issue for product opens with the heatmap and a sample session. Nobody had reported it.

Impact check: dead clicks on #download-pdf went from 14 to 0 after PR #1. "FB-101 fix confirmed."

Evals: 152 cases replayed, FB-103's developer answer included. "copy · frontend": 40 cases, 100% merged unchanged, no reverts. It becomes trusted.

Say: "Most users never click Feedback. The heatmap shows where they struggle anyway. And every developer decision teaches the gate."

Moment 3 · Same kind of fix, no developer

We click: Feedback from another forwarder: "Weight column says lbs, but these are kg."

The graph runs: triage (copy bug, p 0.97) → repro test fails → one-line fix → tests pass → PR.

Merge gate: "copy · frontend" trusted, p 0.97 ≥ 0.85, 1 changed line. Auto-merged, forwarder notified. No developer click.

Say: "Once a kind of fix is proven, developers stop seeing it. Logic bugs, billing and low scores still go to a human."

Moment 4 · One map for both sides

We click: Shared map → Invoice screen. Toggle Forwarder / Developer.

Forwarder view: how colleagues check and send an invoice, "Fixed today: Download PDF works again". Developer view: route, files, the PR #1 test, and the hotspot it came from.

Say: "The same data that fixes bugs onboards people. A new developer's first day is this map, and their first task already has a failing test."

IDs, counts and scores are illustrative and come from the fixtures.
